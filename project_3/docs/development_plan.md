### Phase Four: Fixed Probability Counter Implementation

Implement the probabilistic counter that increments with fixed probability p equals one-quarter. **CRITICAL STREAMING METHODOLOGY**: The correct way to test your fixed probability counter is to process the entire stream multiple times with different random seeds, not to process each temperature separately using known counts. This distinction is fundamental to streaming algorithms and getting it wrong invalidates your entire experimental methodology.

Here is the correct approach for running multiple trials. For each trial from one to fifty or one hundred, you create a fresh FixedProbabilityCounter instance and set a new random seed derived from your master seed (for example, random.seed(42 plus trial_number)). Then you process the entire stream of 3,946 observations in order, calling process once for each observation regardless of what temperature value it contains. The counter does not know or care which specific temperature is being processed—it simply increments probabilistically for each event in the stream. After processing all 3,946 observations, you extract count estimates for all temperature values from this single counter.

The challenge is that your FixedProbabilityCounter as described maintains only a single global counter C, but you need separate counts for each temperature. Therefore, you must modify the implementation to maintain a dictionary of counters, one per temperature, all sharing the same probability parameter but incrementing independently. Your revised implementation looks like this:

```python
class FixedProbabilityCounter:
    def __init__(self, p=0.25):
        self.counters = {}  # Maps temperature -> counter value
        self.p = p
    
    def process(self, temperature):
        """Process a single temperature value from the stream."""
        if temperature not in self.counters:
            self.counters[temperature] = 0
        
        # Probabilistic increment for this specific temperature
        if random.random() < self.p:
            self.counters[temperature] += 1
    
    def estimate(self, temperature):
        """Return estimated count for a specific temperature."""
        if temperature not in self.counters:
            return 0
        return self.counters[temperature] / self.p
    
    def get_all_estimates(self):
        """Return dict mapping temperatures to estimated counts."""
        return {temp: self.counters[temp] / self.p 
                for temp in self.counters}
```

With this implementation, you can correctly run streaming trials. Each trial processes the full temperature stream in order, maintaining separate probabilistic counters for each unique temperature encountered. After the stream completes, you extract all estimates using get_all_estimates. You repeat this entire process fifty to one hundred times with different random seeds to build up a distribution of estimates for statistical analysis.

**Why this matters**: The streaming approach respects the fundamental constraint that you do not know in advance which temperatures will appear or how frequently. A real streaming application processes data as it arrives without look-ahead or replay capabilities. Your experimental methodology must honor this constraint even though you happen to have the full dataset available for analysis. Processing individual temperatures offline using their known exact counts would be testing a completely different algorithm that has access to ground truth, which defeats the purpose of approximate counting.

When evicting to make room, remove the minimum item from your dictionary, then add the new temperature with count equal to minimum count plus one and error equal to minimum count. This initialization is crucial because it accounts for the possibility that the new item appeared during the period when you were not monitoring it. The error field min_count explicitly tracks this potential over-estimation, giving you the error bound that is central to Space-Saving's theoretical guarantees.

Let me provide a concrete implementation example to make this clear:

```python
class SpaceSaving:
    def __init__(self, k):
        self.k = k
        self.monitored = {}  # Maps temperature -> (count, error)
    
    def process(self, temperature):
        """Process a single temperature from the stream."""
        if temperature in self.monitored:
            # Already monitoring this temperature
            count, error = self.monitored[temperature]
            self.monitored[temperature] = (count + 1, error)
        
        elif len(self.monitored) < self.k:
            # Have space to add new item
            self.monitored[temperature] = (1, 0)
        
        else:
            # Must evict minimum to make room
            min_temp = min(self.monitored.keys(), 
                          key=lambda t: self.monitored[t][0])
            min_count = self.monitored[min_temp][0]
            
            del self.monitored[min_temp]
            self.monitored[temperature] = (min_count + 1, min_count)
    
    def get_top_n(self, n):
        """Return the n most frequent items with counts and errors."""
        items = sorted(self.monitored.items(),
                      key=lambda item: item[1][0],
                      reverse=True)
        return items[:n]
    
    def get_monitored_items(self):
        """Return all monitored items with counts and errors."""
        return dict(self.monitored)
```

This implementation provides the core functionality you need. The finding and eviction of the minimum count item is done with a linear search through the monitored dictionary, which takes order k time.
